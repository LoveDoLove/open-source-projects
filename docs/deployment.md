# Deployment and observability

This document outlines the hosting architecture on Cloudflare and how to manage deployments.

## Hosting model

The project is hosted entirely on [Cloudflare Workers](https://workers.cloudflare.com/), using the [Static Assets](https://developers.cloudflare.com/workers/static-assets/) feature. This unified hosting model serves both the static web application and the worker logic responsible for Markdown content negotiation for AI agents.

### Cloudflare Pages removal

Previously, this project used Cloudflare Pages. This was migrated to Cloudflare Workers to consolidate hosting onto a single platform. The Pages workflow was deleted on 2026-09-01 (commit 58a9aee) only after the Workers build was verified to be functioning correctly.

## Automated deployment

Cloudflare Workers Git integration manages deployment:

1. The project is connected to the GitHub repository.
2. The deployment targets the main branch.
3. Every push to main triggers an automatic deployment.

This includes both manual commits and automated commits generated by the [metadata pipeline](metadata-pipeline.md) (fetch-repo-metadata.yml).

### Configuration

Deployment behavior is managed in the Cloudflare dashboard. Key settings include:

- Root directory: /
- Deploy command: npx wrangler deploy
- Version command: npx wrangler versions upload

Note: If the Wrangler CLI reports a "Missing entry-point" error during CI, check that the root directory setting in the Cloudflare dashboard is correctly configured to /.

## Observability

The project utilizes Cloudflare's built-in observability features to monitor worker performance, errors, and traffic.

### Wrangler configuration

Configuration is located in wrangler.jsonc:

```jsonc
{
  "observability": {
    "enabled": true
  }
}
```

This ensures request metrics, execution time, and logs are captured within the Cloudflare dashboard, facilitating troubleshooting of any issues occurring at the edge.

## Troubleshooting deployments

### Wrangler CLI version drift
The CI pipeline resolves the latest version of Wrangler (npx wrangler) on every run. Local development uses a pinned version defined in package.json (devDependencies.wrangler). Expect slight differences between local and CI deployment behaviors if Wrangler updates its CLI interface.

### Static asset serving conflicts
The run_worker_first configuration in wrangler.jsonc is load-bearing. 

```jsonc
"assets": {
  "directory": "./public",
  "binding": "ASSETS",
  "run_worker_first": ["/", "/index.html"]
}
```

If the static site is served instead of the Markdown worker when requesting the root path, verify that run_worker_first is explicitly set to include ["/", "/index.html"].
